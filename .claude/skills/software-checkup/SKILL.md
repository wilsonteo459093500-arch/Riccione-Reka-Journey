# 软件体检（固定流程）

用户是不写代码的老板。每隔一段时间会问「这个软件怎么样、接下来做什么」。每次照同一个流程跑，结果才比得了、不会漏。
这份流程是 2026-11-19 第一次给 KIRA 体检时定下来的，踩过的坑都写在对应的步骤里。

沟通方式照 `CLAUDE.md`：中文、说结果不讲实现、能让用户决定的用选项问。

## 开场（1 分钟内）

1. 用一句话说你理解的任务。
2. 说这次是哪一种，用户没指定就用选项问一次（两种的用量差很多，这是用户该做的决定）：

   | | 快检（默认） | 全面体检 |
   |---|---|---|
   | 做法 | 自己一个人看，挑最要紧的亲手查证 | 最多 7 个角度各 1 个检查员，严重 / 高的发现再交给 2 个复核员（共 9 个以内，用 Workflow） |
   | 时间 | 约 30–45 分钟 | 约 40–60 分钟（看机器能同时跑几个，见第 3 步） |
   | 用量 | 少 | 很多 |
   | 适合 | 大部分时候 | 准备给团队正式用之前、要做大决定之前，而且**刚开一个新的 5 小时额度窗口、这段时间不做别的** |

   用户没选、或额度看起来不宽裕，就做快检。第一次体检（2026-11-19，KIRA）开着 ultracode 派了 14 个检查员，两次都在几分钟内把 5 小时额度用完、一个都没跑完，最后是快检做出来的 —— 所以快检是默认，全面版缩成 9 个以内。

3. 给第一个预计时间。之后时间变了要马上更正（见「进度和剩余时间」）。

## 七个步骤

### 1. 找到软件，确认检查哪一版

不要假设软件就在当前文件夹或 main 里。KIRA 第一次体检时，代码在一条没合并的分支上，main 里只有几句提到它的话。按这个顺序找，找到就停：

1. 仓库里搜名字（目录名、README、`CLAUDE.md`）。
2. 远端分支和还开着的 PR（标题常带软件名）。
3. Vercel 项目：正式版是从哪条分支、哪个 commit 构建的；最近的部署有没有失败。
4. Supabase 项目：有哪些表、几笔资料、几个账号（看得出实际有没有人在用）。

然后说清楚两件事：**正式版是哪一版**、**最新做好但没上线的是哪一版**。检查最新那版，每个问题标明「正式版也有 / 只在没上线的那版」。
名字对不上（用户打错、叫法不同）就先确认，不要猜错软件白跑一小时。

### 2. 打底：测试和构建

在暂存区用 `git worktree` 检出要检查的那一版（不要动当前工作目录，也不要在被检查的代码里改任何东西），装依赖，跑它自己的测试和构建，把数字告诉用户（例：「284 项测试全过、构建成功」）。
这一步的结果也要交给后面的检查员，他们就不用各自再跑一遍。

### 3. 体检：多个角度 + 独立复核

七个角度和各自要看什么，在 `references/audit-angles.md`。软件没有的部分就跳过那个角度（例：没有 AI 功能就不看 AI）。

- **快检**：自己走一遍这七个角度，不派帮手。省力的查法（都是第一次体检时管用的）：
  - 「钱对不对」：写十几行的小脚本直接调用真正的计算函数，同一份单子比每一种输出、每一个版本的逐行合计和小计；比「手动加的」和「自动加的」同尺寸价钱。
  - 「实际操作」：软件自带浏览器测试就先跑它（看清楚它要哪个端口），再决定要不要自己截图看。
  - 文档写的和实际对不对得上，去 Vercel / Supabase 看一眼（例：文档说和旧工具同一个资料库，实际是另一个）。
  - 每条发现自己再查一次才写（看代码 + 跑得出来）；来不及查实的，放进报告的「没查完的线索」，不要写成结论。
- **全面体检**：用 Workflow 跑 `scripts/audit-workflow.js`（用法写在文件开头），把第 1、2 步查到的事实通过 `args` 传进去。
  - 先看机器能同时跑几个：`nproc` 减 2。4 核的机器一次只跑 2 个 —— 报时间之前先算这个。
  - 一启动就全部失败、原因是用量额度：告诉用户几点重置。**不要马上重试第二次**；改做快检，把全面版留给下一个额度窗口（`resumeFromRunId` 可以接着跑，完成的不会重做）。
  - 检查员中途被打断时，他们在暂存区留下的脚本常常已经抓到东西：自己跑一次、看懂、查实了才用。

两种都守这几条，原因写在后面：

- **只读**。体检的对话不改被检查的软件 —— 修是后面各阶段的事，要用户看过计划、选了才动手。
- **不碰正式环境**。不往正式网址发请求、不写正式资料库；读设定和笔数可以。检查员一律只用 localhost。
- **每条发现都要有证据**（哪个文件哪一行、跑了什么脚本、哪张截图），并且**要再查一次、试着推翻它**（全面版由复核员做，快检自己做）。推翻不了的才写进报告；只对一半的，写清楚哪一半是真的。这是「AI 只能建议、不能编」用在体检上：讲错一条，老板就不知道其他的还能不能信。
- 也要写**做得好的地方**，老板才知道哪些不要动。

### 4. 面试老板（两轮，用选项问）

用户明确要求被面试。用 AskUserQuestion，每轮最多 4 题，每题自己就看得懂（带上引出这个问题的事实），推荐的选项放第一个。

- **第一轮：体检在跑的时候问**（不用等结果的问题，省用户的时间）：
  - 现在实际谁在用、用到什么程度（先看资料库的笔数，把数字带进问题里）
  - 想要它做到什么（用户这次特别问的那件事，例：AI 自动报价要哪一种）
  - 能接受的标准（例：预估价和签约价差多少可以）
  - 以后谁来维护哪些东西（例：价格表）
- **第二轮：结果出来之后问**（由发现引出来、只有老板能定的事）：
  - 先做哪个方向
  - 要老板自己动手或点头的事（例：仓库改成不公开、某个 PR 要不要上线）
  - 第一轮答案引出的追问（例：「还在用旧工具」→ 为什么还没换）

用户的回答会改变计划的重心，要真的照着改，不是问完照原来的写。

### 5. 用户问的「未来能不能…」

用户常顺带问一个大问题（例：「以后能不能 AI 自动给客人报价？」）。单独回答，结构固定：

1. 一句话结论：能 / 部分能 / 现在不建议，和为什么。
2. 现在已经有的积木（从代码里指出来，不是泛泛而谈）。
3. 还缺什么，最大的风险是什么。
4. 分几步走到那里，每一步怎么知道可以走下一步（用数字验证，不是感觉）。
5. 大概花多少（AI 费用按次估）。

涉及 Claude API、选 model、agent 的，先读 `claude-api` skill，不凭记忆。

### 6. 出报告 + 分阶段计划

照「报告模板」。计划的每个阶段都要写：目标、做什么、怎么算做完、建议的 model 和 effort、要不要开新对话、新对话的开场白。
model 和 effort 怎么选、几时开新对话，照 `references/model-effort-guide.md`（里面的型号有日期，过期了先核对再用）。

排阶段的原则：

1. 先堵会出事的（钱算错、资料会丢、资料外泄）。
2. 再清掉挡住「真的有人用」的东西 —— 没人用的软件，加功能没有意义。
3. 然后才是新功能，一个阶段只做一件事，一个阶段一个 PR。
4. 大而不确定的事（例：全自动报价）前面放一个便宜的验证阶段，过了才往下做。

### 7. 存档和交接

- 完整报告存成 `docs/checkups/<软件>-<YYYY-MM-DD>.md`（下次体检可以对比上一份）。
- `CLAUDE.md` 加或更新这个软件的一小节：代码在哪、怎么上线、这次面试定了什么（写日期）、各阶段一行、新对话的开场白。保持短，细节指向报告。
- commit、推到这次对话指定的分支、开 draft PR。用户说「合并」才合并。

## 进度和剩余时间

用户要求一路听到进度。每完成一步说一句，格式固定：

> 已完成 3/7：测试 284 项全过。现在：7 个角度并行检查。**预计还要约 50 分钟。**

- 预计时间一变就马上说，并说原因（例：「机器一次只能跑 2 个，要 60 分钟，不是刚才说的 20 分钟」）。
- 后台在跑、自己在等的时候，不要干等：做面试、写第 5 步的可行性、准备报告骨架。
- 出错（额度用完、检查员失败）照实说发生了什么、还剩哪些没跑，不要含糊带过。

## 报告模板

对话里的回复和存档文件都照这个顺序，用白话：

```markdown
# <软件> 体检 · <日期>

## 一句话结论
## 检查的是哪一版（正式版 / 最新版，各是哪天的）
## 评分（每个角度 0–10，一行一句话）
## 做得好的（不要动）
## 要处理的问题
按严重度排。每条：发生什么事（白话）· 影响谁 · 建议怎么做 · 工作量（小 / 中 / 大）· 正式版有没有
## <用户问的大问题>可行吗
## 分阶段计划
| 阶段 | 目标 | 做完的标准 | model · effort | 新对话？ |
每个阶段下面附「新对话开场白」，用户可以直接复制。
## 要你决定的事（已经问过的写答案和日期，还没定的列出来）
## 这次没检查到的（照实写）
```

对话里的最后一条回复要短：结论、最要紧的三五件事、计划表、还要用户定的事；细节指向存档文件。

## 常见情况

- **软件很小或刚开始做**：快检就够，七个角度里没有的直接写「还没有」。
- **上次体检过**：先读 `docs/checkups/` 里上一份，报告里加一段「和上次比」：哪些修好了、哪些还在、新出现的。
- **用户只想要计划、不要体检**：还是做第 1、2 步（不知道现状排不出靠谱的计划），第 3 步用快检。
- **`CLAUDE.md` 里「决定不做的」**：不要再放进建议里。
