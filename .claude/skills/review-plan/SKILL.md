# 先看 → 做计划 → 问清楚 → 才动手

用户（溪岸 / RICCIONE REKA，不写代码）要的是一个**固定的做法**：先把东西看清楚，给一份分阶段的计划，把该问的问完，
他说「可以」才开始改。每次都照下面的顺序跑，不跳步。

## 四条铁律

1. **计划没被用户说「可以 / 开始」之前，不改产品代码。**
   只读的事都可以做：读代码、跑测试、开浏览器实测、截图、查线上部署状态。
2. **边做边报，每次都说还剩多久。**
   - 每进一个步骤先说一句：现在做什么、**大约还要多久**。
   - 等超过 5 分钟就再报一次；估计错了**马上更正**，说明为什么（例：「机器只能同时跑 2 个，改成约 1.5 小时」）。
   - 时间是估计，说「大约」；不要闷着做到最后才一次讲完。
3. **用中文，讲结果和怎么用，不讲实现细节。** 用户能做的决定，用选项问（推荐的放第一个）。
4. **每条问题都要有证据**（哪个文件、怎么确认的、截图）。拿不准的照实说「还没确认」，不要编。

## 步骤

### 0. 找到目标（约 2 分钟）
- 在 repo 里找到要看的东西在哪、多大、最近改了什么，读它的 README。
- 用一句话告诉用户「这是什么、在哪里」，以及整个流程大约多久。
- 用户说的名字对不上任何东西：列出最像的两三个，用选项问。

### 1. 只读审查（最花时间；在后台跑）
- 有 Workflow 工具就用多人审查（这个 skill 就是许可）：每个角度一个审查员，再由复核员逐条尝试推翻。
  没有 Workflow 就自己看，角度少一点，照样要有证据。
- **省额度（2026-11-19 的教训）**：一个会开浏览器实测的审查员大约用 60 万 token、15 分钟；这台机器同时只能跑 2 个。
  第一次一口气派 7 个 + 3 个复核，跑到第 2 个就把账号的 5 小时用量额度用完，后面全部中断。所以：
  - **预设 3 个审查员 + 1 个复核员**（把相近的角度合在一起），大约 40 分钟。
  - 开跑前告诉用户「这会用掉不少额度」；用户说要彻底才加到 7 个，而且分两次跑。
  - 最重要的角度排最前（先交回的最有用）：通常是「实际走一遍」。
  - 中途额度用完：照实说做完了几个、哪些没做，不要当成全部做完；已有的发现马上存进仓库（见步骤 3）。
    额度恢复后用同一个 workflow 续跑（做完的不会重做）。
  - 复核员没跑成：最重要的几条自己对一次代码再报，并说明「没经过复核」。
- 角度按目标挑，常用的：
  1. 电脑上把整个流程实际走一遍（截图）
  2. 手机 / 平板上走一遍，加载速度、离线
  3. 核心规则与资料安全（会不会丢资料、算错）
  4. 产出的东西（PDF / PPTX / 图）对不对、好不好看
  5. 给客户看的内容准不准（对照 `riccione-company-profile`、`interior-design-expert` 两个 skill；CLAUDE.md 的三条原则）
  6. 安全与隐私（repo 是公开的；客户名字、平面图）
  7. 工程健康（测试、结构、以后好不好改）
- **另外自己查线上**（审查员看不到）：线上跑的是不是最新版、该设的环境变数设了没、最近有没有报错。
  只读；要改线上设定、重新部署，先问用户。

### 2. 第一轮面试（趁审查在跑时问）
- 用 AskUserQuestion，一次最多 4 题，每题自己就看得懂（用户可能只看到问题框）。
- 问不用等审查结果的事：现在用到什么程度、谁在用、用什么设备、最想提升哪方面、用户原话里有歧义的地方。

### 3. 汇总
- 被复核推翻的丢掉，重复的合并，严重度照复核后的算。
- 先讲做得好的（简短），再讲问题：按「会出错 / 丢资料」「不好用」「不好看」「团队 / 线上」「以后难改」分组，
  每条用不写代码的人看得懂的话，说**谁会遇到什么**。关键的附截图。
- 列出「审查没看到 / 没确认」的部分。
- **马上把发现和计划草稿存进仓库**：`.claude/plans/<app>.md`（标明「草稿，等用户确认」），提交、推送。
  不要放进 app 的文件夹：静态网站会把它当网页放上线，合并时还会触发那个 app 重新部署。
  审查结果只在临时文件夹里，对话一断就没了；新对话也要靠这份接着做。

### 4. 分阶段计划
- **一个阶段 = 一个 PR = 一个新对话。** 每个阶段写：
  做完得到什么（结果）· 为什么排这里 · 大约多久 · 用什么 model · 什么 effort · 新对话的开场白。
- 排序：用户选的优先方向 × 严重度 × 先后依赖。会丢资料、线上坏掉的排最前，除非用户另有决定。
- 需要用户决定的地方标出来（「要你决定」），留到第二轮面试。
- 新功能照 CLAUDE.md：先 brainstorm 几条路和取舍，用户选了才做。

### 5. Model / effort / 几时开新对话（每份计划都要附）

| 做什么 | Model | Effort |
| --- | --- | --- |
| 审查、做计划、brainstorm（这个流程本身） | 最强的（现在是 Fable 5.2） | high |
| 难的阶段：资料保存 / 同步、安全、登入、动到很多文件的改动、查了两次还查不出的 bug | Fable 5.2 或 Opus 5.5 | high（卡住才 xhigh） |
| 一般的阶段：照计划做清楚的功能、界面调整、加测试 | Opus 5.5 或 Sonnet 5.5 | medium |
| 小修：改字、换图、调颜色、改 README | Sonnet 5.5（或 Haiku 5.5） | low |

- `max` 基本不用：官方说明写它收益递减、容易想太多。
- **在对话一开始就选好** model 和 effort，中途不要换（换了要整段重算，又慢又贵）。
  对话里打 `/model <名字>`、`/effort <low|medium|high|xhigh>`。
- 型号会更新：写计划前用 `claude-code-guide` 查一次现在有哪些 model、预设 effort 是什么，不要凭记忆。

**几时开新对话**
- 每个阶段做完、用户说「合并」之后 → 下一阶段开新对话。
- 换 app、换话题 → 开新对话。
- 同一个问题纠正两次还是不对 → 开新对话，把问题讲得更清楚（比第三次纠正有效）。
- 对话很长、开始忘记前面讲过的 → 开新对话。
- **不要**在一个阶段做到一半（PR 还没做完）时换对话，除非卡住。
- 开场白照 CLAUDE.md 的写法：「继续做 <app>（<文件夹>/）……这次要做：计划第 N 阶段」。计划写在 CLAUDE.md，新对话会自己读到。

### 6. 第二轮面试
- 问审查带出来的决定：要不要花钱（AI、云端）、范围要多大、两种做法选哪个、哪几个阶段要做。
- 用户说「不做」的，记进 CLAUDE.md「决定不做的」，以后别再提。

### 7. 用户说「可以」之后
- 把 `.claude/plans/<app>.md` 从草稿改成定稿（写进用户的决定），CLAUDE.md 留一小段指过去（写清日期），开 draft PR。
- 这个对话还短 → 可以直接做第 1 阶段；已经很长 → 请用户开新对话，给他开场白。
- 之后每个阶段照 CLAUDE.md：draft PR + 预览链接 + 截图，用户说「合并」才合并。

## 回报的样子（每次都这个顺序）

1. 一句话结论：这个东西现在怎么样。
2. 做得好的（3 条以内）。
3. 最重要的问题（5–8 条，分组，附证据）。
4. 分阶段计划表（含 model / effort / 多久 / 开场白）。
5. 几时开新对话。
6. 要你决定的问题（选项）。
7. 没看到 / 没确认的部分。
