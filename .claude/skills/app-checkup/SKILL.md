# 软件体检（固定流程）

用户是不写代码的老板。他说「帮我看 X 这个软件怎么样、有什么要提升、做个分阶段计划」时，**每次都照这个流程跑**，这样他每次拿到的东西都一样，可以互相比较。

这种对话**只出结论和计划，不改 app 的代码**（`CLAUDE.md`：先 brainstorm 再执行）。用户挑了要做哪个阶段，再开新对话动手。唯一会进 repo 的是计划本身（`<app>/PLAN.md`）和 `CLAUDE.md` 里的一行指引。

## 用户每次会拿到的 5 样东西

1. **体检结论**：做得好的 + 要改的，按「对他的影响」排，不按技术分类
2. **分阶段计划**：写进 `<app>/PLAN.md`，下一个对话读得到
3. **每个阶段**：用什么 model、什么 effort、要不要开新对话、开场白那一句
4. **面试两轮**：用选项问，不让他打字
5. **全程进度**：每一步说做到哪、还剩大概几分钟

## 全程规则

- **报进度 + 剩余时间**（用户明确要的）。每做完一步、每等超过两三分钟，都说一句，格式固定：

  `**进度 3/6 · <刚做完什么>**。<现在在做什么>。**全程还剩约 N 分钟。**`

  估不准、出了状况（中断、要重跑）就照实说原因和新的时间。不要为了看起来准而不报。
- **只读**。不改 app 的档案、不碰线上资料。临时脚本、截图放 scratchpad，不放 repo。
- **线上只看结构和数量**：表有几行、部署成不成功、环境变数的名字。不读联系人 / 客户的内容，不读密钥的值。线上的事由主对话自己查，**不交给体检的人**（见第 1 步）。
- **每个结论都要有证据**，没核实过的不写进计划。被「怀疑者」推翻的发现要删掉，并照实说推翻了几个。
- 跟用户讲**结果和影响**，不讲实现细节。决定用选项问。

## 用量：这种对话很吃用量

十几个人同时查一个 app，会用掉帐号 5 小时用量里很大一块。2026-11-19 第一次跑就在中途撞到上限，七路全断、要重跑。所以：

- 开场就告诉用户「这次会用掉不少用量，最好在用量刚重置之后跑」
- 体检的人用 **Opus 5.5**（`model: 'opus'`），不要跟着主对话用 Fable
- 中途撞上限：照实说，等重置后重跑。同一个对话里可以用 `resumeFromRunId` 接回已经跑完的人

## 步骤

### 0　开场（1 分钟内）

先找到是哪个 app（根目录 `README.md` 开头列了全部 app 和资料夹；名字对不上就问）。然后发第一则讯息：一句话说找到了什么 + 下面这张表 + 全程预计时间（顺利的话 35–45 分钟）。

| 步骤 | 做什么 | 大概 |
|---|---|---|
| 1 | 摸底：读计划、跑测试和构建、看线上状态 | 5 分钟 |
| 2 | 分 4 组同时体检，每个发现再找人反驳一遍 | 15–20 分钟 |
| 3 | 体检跑的同时，面试第一轮 | 同时进行 |
| 4 | 整理发现；面试第二轮（取舍） | 5–8 分钟 |
| 5 | 分阶段计划 + model / effort / 新对话 | 5 分钟 |
| 6 | 存进 `PLAN.md`、开 draft PR | 3 分钟 |

### 1　摸底（自己做，不派人）

- 读 app 的 `README.md` / `PLAN.md` / `DEPLOY.md`：做了什么、承诺了什么、哪些写着「还没用真的资料测」「没做（以后可以加）」
- 档案大小排行（哪里最大、最复杂）
- 跑测试和构建，记下结果和打包大小（`dist/` 已在 `.gitignore`）
- **线上状态和真实用量**（Vercel / Supabase 的只读工具，用 ToolSearch 载入）：
  - 正式版在不在、是不是最新（跟 main 上这个 app 最后一个 commit 比）、最近的预览部署成不成功
  - 环境变数**有哪些名字**（少了哪个 = 哪个保护没开）
  - 每张表几行、安全建议
  - 看到可疑的数字（例如 1 个人却有 13 笔记录），自己跑一个**只看时间和类别、不看人名电话**的统计查清楚
- 把核实过的事实一条一句列好，下一步交给体检的人。他们拿到这些，就不用、也不准自己去碰线上

**真实用量是最有用的一个事实** —— 功能做了很多但资料库几乎是空的，重点就不是再加功能，而是让它用起来。

### 2　多路体检（Workflow，背景跑）

用户叫这个 skill 就是同意跑多路体检。脚本是这个 skill 资料夹里的 `workflow.js`。

**一定要拆成 4 组、在同一则讯息里同时开 4 个 Workflow**（各带不同的 `only`）。一个 Workflow 一次只同时跑「CPU 数 − 2」个人，云端机器是 4 核 = 2 个；不拆的话七个方向要排队，一个多小时都跑不完。

| 组 | `only` |
|---|---|
| 1 | `["security", "ai"]` |
| 2 | `["dataops", "logic"]` |
| 3 | `["uxapp", "uxpublic"]` |
| 4 | `["product"]` |

`args`（真的 JSON，不要包成字串；四组除了 `only` 和 `hints` 都一样）：

| 栏位 | 填什么 |
|---|---|
| `root` / `app` | repo 和 app 资料夹的绝对路径 |
| `name` | app 的名字 |
| `about` | 一段话：这是什么、谁在用、怎么用（手机 / 电脑、什么场合）、限制（预算…）。**面试第一轮问到的也写进来**。体检的人靠这段判断「对老板有多严重」 |
| `facts` | 第 1 步核实过的事实，一条一句。加一句「省着用：大约 50 次工具呼叫内做完；不准用资料库 SQL 工具」 |
| `scratch` | scratchpad 底下的一个资料夹 |
| `model` / `effort` / `verifyEffort` | `"opus"` / `"high"` / `"medium"` |
| `hasAI` | app 有没有呼叫 AI |
| `runNotes` | 本机怎么跑、怎么登入、有哪些页面、怎么塞样例资料。没法跑就留空，会跳过「实际操作」 |
| `publicNotes` | 有没有给外人看的页面、怎么打开。没有就留空 |
| `hints` | 每个方向先读哪些档案、特别要查什么（`security` `ai` `dataops` `logic` `uxapp` `uxpublic` `product`）。写得越具体，发现越准 |
| `only` / `skip` | 这一组查哪几个方向 / 这次不查的方向 |

七个方向：安全与隐私 · AI 调用 / 费用 / 等待体验 · 资料可靠性与上线维护 · 核心计算 · 实际操作（Playwright 真的点一遍）· 给外人看的页面 · 产品缺口。每个方向查完，由另一位「怀疑者」逐条尝试推翻并补漏。

先用 `dryRun: true` 跑一次可以检查 args 有没有填对（不派人、几秒就回来）。

### 3　面试第一轮（体检在跑的时候问）

用 AskUserQuestion，最多 4 题，每题自己就看得懂（他可能只看到题目，看不到前面的讯息）。问**代码回答不了**的事：

- 现在实际怎么用？卡在哪里？（把真实用量的数字放进题目）
- 接下来一两个月最想它帮你做到什么？
- 资料 / 客户 / 档案现在在哪里？（决定导入、搬家要先做哪种）
- 他的要求里有歧义的词，在这里问清楚

最好在放出体检**之前**问完，这样答案可以写进 `about`；来不及就体检一放出去马上问。

### 4　整理 + 面试第二轮

- 删掉被推翻的；严重度用怀疑者改过的；不同方向讲同一件事的合并
- 翻成老板的话，分四类：**会出事，先修** · **让它真的用起来** · **用起来更顺** · **可以晚点**
- 照实报数：几个发现、几个被推翻、哪个方向没跑完
- 第二轮面试（最多 4 题）：只问这些发现带出来的**真取舍** —— 先后顺序、要不要砍掉某样、需要他本人去做的设定。有惯例答案的不问，直接选了写进计划

### 5　分阶段计划

每个阶段写：

- **目标**（一句老板的话）和**做完他会看到什么**
- 做什么（3–6 条）、怎么验收（尽量用真资料、真手机）
- 大概几个对话
- **model · effort**（照下面的表）
- **开新对话？** + 开场白：「读 `<app>/PLAN.md`，做体检计划第 N 阶段」

排法：

- **第 0 阶段永远是「不用写代码、你现在就能自己做的」**（开一个设定、补一个环境变数…），有就列，没有就跳过
- 会漏资料、丢资料、乱花钱的排最前
- 接着是「让它真的用起来」的，再来才是新功能
- 一个阶段 = 一个对话做得完、合得进去的量；太大就拆

### 6　存档

- 在 `<app>/PLAN.md` 加一节「体检 YYYY-MM-DD」：面试结论、发现（按四类）、分阶段计划表。旧的内容不删
- `CLAUDE.md` 加 / 更新一行指引（写日期）
- commit、push、开 draft PR。用户说「合并」才合并

### 7　最后一则讯息

短。顺序固定：一句总评 → 做得好的（3 条内）→ 要改的（按四类，各挑最重要的）→ 计划表（阶段 · 目标 · model · effort · 新对话）→ 他现在自己能做的事 → PR 链接。细节在 `PLAN.md`，不要整份贴出来。

## model · effort · 几时开新对话

| 这个阶段的性质 | model | effort |
|---|---|---|
| 体检、做计划、大范围审查（就是这种对话） | Fable 5.2（派出去体检的人用 Opus 5.5） | high |
| 安全、资料库结构、搬资料、做错会丢资料 / 漏资料的 | Opus 5.5 | high |
| 上面这类如果牵涉很多档案，或 Opus 试过一次没做好 | Fable 5.2 | high |
| 一般新功能，验收写得清楚 | Opus 5.5 | medium |
| 画面、排版、文案、照已有做法再加一块 | Sonnet 5.5 | medium |
| 改一句字、换一张图、问一个问题 | Sonnet 5.5 | low |

- **xhigh / max 平常不用**。同一个问题用 high 试了两次还没解决，才升一级；解决了就降回来。越强的 model、越高的 effort，用量扣得越快、也越慢。
- 拿不准选哪个：选 **Opus 5.5 · medium**。

**开新对话的时机**

- 每个阶段开一个新对话
- PR 合并之后（那条分支结束了）
- 要换 model 的时候
- 换去做另一个 app
- 对话已经很长：Claude 开始要你重复讲过的事、或同一个错改了两三次还没好

**不用开新对话**：同一个阶段里看了预览要调整、小修小补。

## 这个流程学到的事（2026-11-19 第一次跑 SPACE）

- **不拆组会跑不完**：一个 Workflow 在 4 核机器上一次只跑 2 个人。拆成 4 组同时开，七个方向才是真的同时在查
- **会撞用量上限**：第一次用 Fable 派 7 个人，6 分钟就撞到 5 小时上限、全部白跑。体检的人用 Opus，并在 `facts` 里提醒省着用
- **线上的事主对话自己查**：部署状态、环境变数名字、行数、可疑数字，先查好写进 `facts`。体检的人就不用碰线上，也查得更准
- 体检的人同时在跑，要各自的端口和各自的 scratch 资料夹（`workflow.js` 已经分好）
- 这台机器的截图只有 unifont 能显示中文 —— 字体难看不算发现
- `about` 和 `facts` 写得马虎，发现就会偏技术、离老板的实际情况很远
- 用户说的「streaming responses + remaining time」是指**对话时**边做边报进度（2026-11-19 问过），不是要在 app 里加功能
